# Launch (increment 8) — runbook

The last increment. It adds no migration and no clock. It is the order in which everything
that has been merged since increment 2a reaches `factions_live`, the two things that must
be true on the game server, the grace stamp, and the acceptance that says the product the
guide describes is the one that is running. Nothing here is automatic; every step is a
decision.

⚠️ `factions_live` is touched only by the runbooks this document names, in their order,
each by its own procedure. Nothing applies migrations at startup (`CLAUDE.md`). Stop the
bot before any migration that adds a NOT NULL column; each runbook says whether it does.

## 1. The game server

Through the Nitrado web panel, by hand. None of this is the bot's, and none of it can be
undone by a redeploy.

1. **Delete the stale `flag-supplies.json`** in the mission's `custom/` directory
   (`CLAUDE.md` known-open item 3; spec §12). It is a 30 KB leftover from before the
   supplies design; `faction-supplies.json`, beside it, is ours. Before deleting: open
   `cfggameplay.json` and confirm `WorldsData.objectSpawnersArr` names
   `./custom/faction-supplies.json` and does **not** name `./custom/flag-supplies.json`.
   If it does name it, stop — that is a different server state than any spec describes;
   do not delete a file the server loads. Then delete `flag-supplies.json` from the file
   browser. No restart is needed for a file nothing loads.
2. **Set the raid window for today.** `docs/deploy/raid-window.md`: if launch falls
   inside Friday 00:00 UTC → Monday 00:00 UTC, `GeneralData.disableBaseDamage` is
   `false`; otherwise `true`. Read it back. The restart in step 4 applies it.
3. **Confirm `FlagRefreshMaxDuration` is 7 days** (spec §12: the guide's 7-day clocks
   assume it; a change here is a guide change, not a config change). Do not change it.
4. **Restart the server** once, after 1–3, and watch the next ADM file arrive:

       docker exec clan-wars-postgres-1 psql -U factions -d factions_live -X -c "select filename, boot_at, complete from adm_files order by id desc limit 2"

   A new `filename` with a `boot_at` after the restart, within one ingest sweep.

## 2. The launch grace stamp

Every pole the log has ever seen gets 7 days from the launch instant before it can appear
on the public-bases layer (spec §4.2). The declarations runbook stamped `now() + 7 days`
on its deploy day; this replaces that with the real launch instant, from the repo root on
the host, with the bot stopped:

    sudo systemctl stop clan-wars-bot
    cd /opt/clan-wars && DATABASE_URL=<the .env value, ending in /factions_live> pnpm launch --server 1 --at <launch instant, ISO 8601 UTC>

`--at` is the instant the launch is announced, e.g. `2026-09-12T00:00:00Z`. Re-running
with the same `--at` is the same stamp; there is no default, so a bare re-run cannot
invent a later one. Expected output, one line of JSON: `{"polesStamped":<n>,"graceUntil":"<at + 7 d>"}`.

Then:

    docker exec clan-wars-postgres-1 psql -U factions -d factions_live -X -c "select count(*) filter (where grace_until > now()) as in_grace, count(*) as total, min(grace_until), max(grace_until) from poles where server_id = 1"

`in_grace` equals `total`, and `min` equals `max` equals the printed `graceUntil`.

    sudo systemctl start clan-wars-bot && systemctl status clan-wars-bot

## 3. `/guide`

The site redirects to the guide's own host; nothing to deploy beyond the web image that
increment 8 is part of (`docker compose build web && docker compose up -d web`). Then:

    curl -sI https://dayzclanwars.com/guide | head -3
    curl -sI https://dayzclanwars.com/guide/05-raiding.html | grep -i '^location'
    curl -sI https://fieldguide.dayzclanwars.com/ | head -1

The first is `308` with `location: https://fieldguide.dayzclanwars.com/`; the second's
location ends in `/05-raiding.html`; the third is `200` from GitHub Pages. If the third
fails, the guide's repo (`../field-guide/`, `CNAME`) is the problem, not this site.

## 4. Acceptance — before the announcement

All read-only against `factions_live`, in this order. Record every output.

1. **Scale.** `select count(*) from factions;` — read with the dormancy check below.
2. **The dormancy check**, `CLAUDE.md`'s "Current state" query (the `declarations` join).
   Any row with `age` over 7 days goes dormant on the next tick; on launch day that is a
   decision to make before starting the bot, not a surprise after.
3. **Nothing is declared yet, and the season is open:**

       select count(*) from declarations;
       select id, number, started_at, ended_at, week_closed_through from seasons where server_id = 1 order by number;

   Zero declarations. Exactly one season with `ended_at` null; its `started_at` is the
   launch instant or earlier (a season opened by 4's runbook before launch is fine — the
   dormancy clock coalesces against it, spec §5.1).
4. **Grace**, step 2's query again: `in_grace = total`.
5. **The queues are empty or draining**, none stalled:

       select kind, count(*) from faction_events where posted_at is null group by kind;
       select target, count(*) from clan_notices where posted_at is null and failed_at is null group by target;
       select count(*) from war_log_events where posted_at is null;

6. **Discord**, by eye in the guild: the two clan categories exist and are empty of clan
   channels (no clan is active), `@Linked` and `@Alpha` exist below the bot's role,
   `#clan-feed` and `#war-log` are readable, and `/guest` is the only slash command that
   does anything — the retired names still register and answer with the retirement text
   (`apps/bot/src/retired-commands.ts`), so a player who types `/faction` is told where
   to go rather than seeing nothing.
7. **The site, signed out**: `/`, `/clans`, `/scoreboard`, `/alphas`, `/seasons`,
   `/war-log`, `/players`, `/guide` all answer; `/me`, `/map`, `/clan` redirect to
   `/login`. **Signed in and linked**: `/me` shows the gamertag; `/map` renders with the
   travel-points layer and no bases (nothing is declared); `/link` says already linked.
8. **The numbers**: `pnpm guide:numbers` on a checkout of the deployed commit, then
   `git diff --stat docs/guide-numbers.json` — only `generatedAt` changes. The site, the
   bot and the guide state the same numbers.

## 5. Record

Write `docs/acceptance/<date>-launch.md` with: the deployed commit; the migration id
`drizzle.__drizzle_migrations` reports; the `polesStamped` and `graceUntil` the script
printed; the output of every query in section 4; the three `curl` lines from section 3;
what was NOT exercised (a raid, a defense, a vote — none can happen on launch day). The
record is what the next deploy's precheck reads.
