# Airdrop events — deploy and operate

One locked container, at one of 16 staged Livonia locations, for exactly one
session: when the server is genuinely busy the bot picks a location and a
colour, announces the location about 30 minutes before a restart, registers
that location's spawner in `cfggameplay.json` at the restart, and removes it
again at the restart two hours after that. Spec:
`docs/superpowers/specs/2026-09-20-airdrop-events-design.md`.

## 1. Prerequisite in the `livonia` repo

`livonia/cfggameplay.json`'s `WorldsData.objectSpawnersArr` must not name any
`./custom/airdrop-*.json` file by hand. The `livonia` repo *is* the mission
tree, and publishing a GitHub Release FTPs the whole tree — `cfggameplay.json`
included — over whatever the bot last wrote (`livonia/CLAUDE.md`). If the
baseline still carries a hand-added airdrop entry, every Release re-enables a
drop the bot has already ended, and the bot's own level-triggered repair (§6
below) only ever pushes it back off two hours later — not the same thing as
never having been re-enabled.

⚠️ **As of this writing (2026-09-21) this is already satisfied.** `v1.6.65`
put `./custom/airdrop-dolnik-blue.json` back on the map by hand, and `v1.6.66`
took it back off; `v1.6.67` (the current `main`/latest release) carries no
`airdrop-*` entry. Confirm before every future deploy anyway — the entry has
gone in and out of this file by hand before, and a Release publishes whatever
`main` holds at that moment, not whatever the last audit found:

```bash
cd livonia && grep -n "airdrop-" cfggameplay.json || echo "clean"
```

If it is not clean: remove the entry from `objectSpawnersArr`, commit, tag,
and publish the Release (publishing is what deploys — pushing `main` or a tag
alone does nothing, per `livonia/CLAUDE.md`).

## 2. Migrate

Migration `0045_aberrant_barracuda.sql` adds `airdrop_events`. Migrations are
applied by the release deployer, never by the bot (`CLAUDE.md`'s "Migrations
are applied automatically on a release deploy, and by nothing else"). On the
auto-deploy path `deploy/deploy-release.sh` runs `pnpm db:migrate --apply
--production` for you, after stopping the writers. Off that path, the manual
procedure is `docs/deploy/2026-09-14-db-migrate.md`:

1. Stop the bot.
2. `pnpm db:migrate` (dry run, prints the tags it would apply).
3. Read the generated SQL.
4. `pnpm db:migrate --apply --production`.
5. Start the bot.

⚠️ Never apply anything to `factions_live` yourself outside that script and
runbook, and never point a manual migrate run at it without `--production` —
the guard in `scripts/migrate.ts` refuses both directions on purpose.

## 3. Env

All in `.env`, never on the start command line — `BOT_FEED_CHANNEL_ID` is the
standing example of what goes wrong otherwise: a value passed only on the
command line turns the feature off at the very next restart with nothing
saying so.

    AIRDROP_TICK=true
    SERVER_EVENTS_CHANNEL_ID=<snowflake>
    AIRDROP_WEEKLY_CAP=1
    AIRDROP_MIN_POP=6

`AIRDROP_WEEKLY_CAP=1` for the first fortnight, per spec §12 — raise to 2
afterward.

⚠️ **`AIRDROP_MIN_POP=6`, not the code default of 5** (amended 2026-09-21). The
default stays 5 because it is the floor for a server nobody has measured; 6 is what
this server's own history argues for. Replayed over 253 decision instants
(2026-09-01 to 09-22) under the high-water rule at cap 2:

| `AIRDROP_MIN_POP` | drops in 21 days | pops they fired at |
|---|---|---|
| 5 | 5 | 5, 5, 6, 8, 10 |
| **6** | **3** | **6, 8, 10** |
| 7 | 2 | 8, 10 |

At 5 two drops land on a pop of 5; at 7 the event becomes too rare to feel live.
This is the lever to reach for if drops feel too frequent or too scarce — **not**
`AIRDROP_HISTORY_MS`, which the same replay shows is nearly inert (3d and 5d both
fire 5 times, 7d through 14d fire 4). `SERVER_EVENTS_CHANNEL_ID` is fatal at config load when
`AIRDROP_TICK` is on and it is unset (`apps/bot/src/config.ts`): with no
in-world marker, the location announcement is the only way anyone ever finds
the drop, so having nowhere to post it is misconfigured, not merely degraded.
`AIRDROP_TICK` also requires `RESTART_SCHEDULE` — config load refuses to
start without it, because a drop is only ever placed or removed at a restart.

## 3a. What actually triggers a drop

Amended 2026-09-21. The population test is a **five-day high-water mark**, not the
p90 the original spec described:

    pop >= max(AIRDROP_MIN_POP, highest decision-instant pop over the last 5 days)

plus the three conditions that did not change — under the weekly cap, 24h since the
last drop, nothing already announced or live. "pop" is the count online 30 minutes
before the restart, and the bar is built from that same measurement at each earlier
restart slot in the window.

⚠️ **Long gaps are normal and are not a fault.** One busy night sets the bar for the
following five days, so a record of 11 on a server that usually peaks at 7 means no
drop until 11 comes back or that night ages out. Before investigating a quiet
fortnight, check the bar the tick is actually applying:

```sql
select decided_at, pop_at_decision, threshold, state
from airdrop_events order by decided_at desc limit 10;
```

`threshold` on each row is the high-water mark that row was judged against. A run of
rows whose `pop_at_decision` sits just under a high `threshold` is the rule working,
not failing. `AIRDROP_MIN_POP` is the lever for how often drops happen, in both directions — see
the table in §3 for what each value did against this server's real history. Shortening
`AIRDROP_HISTORY_MS` is NOT the lever: it is a code change, and the same replay shows
it barely moves the count.

## 4. Verify

```sql
select * from airdrop_events order by decided_at desc limit 5;
```

and the bot's `airdrop:` log lines (`decided`, `enabled`, `ended`, `REFUSED`).
A `decided`/`announced` row whose `announced_at` is still null well after its
slot has passed means the announcement never posted — check
`SERVER_EVENTS_CHANNEL_ID` first.

The one-command end-to-end check is `/airdrop place location:Dolnik`
(Manage Server permission required): it announces immediately, goes in at the
next restart, and comes out at the one after — and, being `manual`, it does
not spend the week's cap.

## 5. The deploy clobber

A `livonia` Release published while a drop is live removes the spawner entry
immediately (§1). The next restart slot puts it back if the `airdrop_events`
row is still `live` — the bot recomputes the wanted file state from the
database every slot (spec §6), not from what the file happened to hold. If
the session has already ended by the time the next slot runs, nothing is put
back, because the row has already moved to `ended`. Either way, don't publish
a `livonia` Release mid-event if it can wait: a drop cut short for a slot or
two is an accepted cost, not something worth engineering around, but it is
also not free to players who were told the container would be there.

## 6. Turning it off

`AIRDROP_TICK=false` stops new decisions immediately, but it does **not**
remove a container already live. In `apps/bot/src/restart-tick.ts`, the code
that disables a drop (`intent.ending`, resolved by `airdropIntent` and applied
inside the `opts.airdrop?.enabled` block) is gated on exactly the same
`AIRDROP_TICK`-derived flag as the code that enables one — `airdropIntent`
itself is only called when `opts.airdrop?.enabled` is true, so flipping the
flag off skips the disable path along with the decide path. A drop that is
`live` when the flag flips off stays registered in `cfggameplay.json`
indefinitely; nothing else will ever remove it.

Safe sequence:

- If a drop is `announced` or `live`, let it run its course first — check
  `select * from airdrop_events where state in ('announced','live')` — then
  flip `AIRDROP_TICK=false` once it reaches `ended` on its own.
- If it must come off immediately, remove the `./custom/airdrop-<location>-
  <colour>.json` entry from `cfggameplay.json` by hand (Nitrado panel, same
  procedure as the raid window's manual fallback in `docs/deploy/raid-window.md`)
  and update the row yourself: `update airdrop_events set state = 'ended',
  ended_at = now() where server_id = … and state = 'live';` — so the database
  and the file agree, and a later re-enable of `AIRDROP_TICK` does not find a
  stale `live` row and try to re-derive intent from it.

## 7. `/airdrop place`

Admins only (`ManageGuild`/Manage Server — Discord hides the command from
everyone else, and the handler checks again). It places a drop at the next
restart, announces immediately the same as an automatic one, and is excluded
from `AIRDROP_WEEKLY_CAP` (`airdrop_events.manual = true`, filtered out of the
weekly count in `airdrop-tick.ts`). It is **not** excluded from anything else:
the 24-hour gap and the one-at-a-time rule both still apply, because the
`open`/`last` lookups that enforce them see every row regardless of `manual`.
It refuses outright ("A drop is already announced or live. Only one at a
time.") while another drop is announced or live, and — like the automatic
path — the row is written `failed` and nothing is placed if the announcement
itself fails to post.

## 8. Rollback

Revert the code. If a drop is registered in `cfggameplay.json` at the time
(check `objectSpawnersArr` for an `airdrop-*` entry, or look for a `live` row
in `airdrop_events`), remove that element from the array by hand — the
reverted code has no tick left running to do it for you.
