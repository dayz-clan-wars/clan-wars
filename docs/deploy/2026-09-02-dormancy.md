# Deploying faction dormancy — 2026-09-02

Shipped `764f976` (faction dormancy) and the 21 commits behind it to the live bot and
ingest worker. Migration `0015` adds `factions.dormant_since`.

## What went wrong, and the rule it produced

CLAUDE.md said migrations apply at bot startup via `runMigrations`. **They do not.**
`runMigrations` is exported from `packages/db/src/migrate.ts` and called only from test
setup; nothing in `apps/bot/src` calls it, and no package defines a `db:migrate` script.
Every earlier migration reached `factions_live` by hand — the fact was never written
down, so the belief survived.

The bot was therefore restarted onto the dormancy code against a database with no
`dormant_since` column, and logged

    dormancy tick failed PostgresError: column "dormant_since" does not exist

once per 10s tick for about four minutes. No damage: the failing statement is the
dormancy clock's read, `guardedRunner` swallows the rejection, and nothing else in the
bot touches the column. Commands, linking and the ceremony tick were unaffected. But a
migration adding a NOT NULL column, or one whose absence broke a write path, would have
been player-visible in the same window.

**Apply the migration as its own deliberate step, before starting the new code.** Do not
phrase it to yourself as "restart and the migration applies" — that sentence is the bug.

## The runner

There is no migrate script, so the migration was applied with a one-off file at the repo
root (needed there for workspace resolution — `@factions/db` does not resolve from the
scratchpad), then deleted:

```ts
import { createClient, runMigrations } from "./packages/db/src/index.js";
const url = process.env.DATABASE_URL;
if (!url) throw new Error("DATABASE_URL unset");
// ⚠️ this script exists to touch the production database; refuse anything else.
if (!url.endsWith("/factions_live")) throw new Error(`refusing: not factions_live -> ${url}`);
const db = createClient(url);
await runMigrations(db);
await (db as any).$client.end();
```

Run with `set -a && . ./.env && set +a && npx tsx ./migrate-live.tmp.ts`.

**Before running it, check the migrator will apply only what you think it will.** The
postgres-js migrator applies every journal entry whose `when` is newer than the newest
`created_at` in `drizzle.__drizzle_migrations`. If the live table was ever filled in by
hand with different timestamps, that comparison can replay old migrations:

    docker exec clan-wars-postgres-1 psql -U factions -d factions_live -X \
      -c "select count(*), max(created_at) from drizzle.__drizzle_migrations"

Here: 15 rows, newest `1788300677726`, exactly `0014`'s journal `when`, against 16
journal entries — so `0015` and nothing else. After: 16 rows, newest `1788370156735`.

## The order that was used

1. Read-only acceptance check (below). One active faction, `COK`, age ~21h — under the
   7-day threshold, so the first tick transitions nothing. **This is the go/no-go**: any
   row over 7 days loses a real player's supplies on the first tick.
2. Full gate: `TEST_DATABASE_URL=… npx turbo run typecheck test --concurrency=1 --force`
   → 20/20 tasks, 0 cached, 455 bot tests.
3. `docker compose build ingest-worker`.
4. `pkill -f "src/main.ts"`, then **count the survivors** — zero before starting.
5. Apply `0015` (above). *This step belongs here, before step 6 — it was learned the
   hard way, after.*
6. Start the bot: `set -a && . ./.env && set +a && nohup pnpm --filter @factions/bot start > bot.log 2>&1 &`
   — note `. ./.env`, not `. .env`: zsh's `.` searches `$PATH` for a slashless name and
   silently fails to find the env file, starting nothing.
7. `docker compose up -d ingest-worker`.

The bot must go first, before the worker: `0015` is additive and nullable, so old code +
new schema is safe, but the worker's drizzle queries emit explicit column lists that
include `dormant_since`.
